# 10 — نشر هاي روت

**القرار:** على خادم موازين نفسه (`54.162.172.204`)، بمشروع Docker مستقلّ،
ونطاقٍ مستقلّ خلف بوّابة Caddy القائمة.

> ⚠️ **الصورة لم تُبنَ بعد.** بيئة التطوير التي كُتب فيها هذا الإعداد تمنع سحب
> صور Docker Hub، فأول `docker build` سيقع **على الخادم**. المُتحقَّق منه:
> `docker compose config` صحيح، وسكربتا الصدفة سليمان نحويًّا، والإصدارات
> واللواحق مقروءة من `composer.json` و`package.json` لا مُخمَّنة. وأول بناء قد
> يكشف لاحقةً ناقصة كما يقع في كل بناء أول — **لا تُزل هذه الملاحظة قبل بناءٍ
> ناجح**، واحتفظ بمخرج البناء إن أخفق.
>
> فابدأ في وقتٍ تحتمل فيه محاولةً أو اثنتين، لا في ساعة ضغط.

---

## 0. ما يعنيه اقتسام الخادم — قبل أن تبدأ

اختيارُ الخادم نفسه يوفّر التكلفة والشبكة، ويحمل ثلاثة أثمان تُعرَف الآن لا بعد
أول عطل:

1. **بوّابة موازين تُعدَّل.** منفذا 80 و443 مشغولان بها، فلا بوّابة ثانية. وإضافة
   نطاق هاي روت تعني تعديل `Caddyfile` في مستودع موازين. **خطأٌ فيه يُسقط
   `mawazinswift.com` معه** — ولذلك الخطوة ٥ تتحقّق من الصيغة قبل التحميل،
   وتستعمل `reload` لا `restart`: إعدادٌ فاسد يُرفض ويبقى القديم عاملًا.
2. **عطلٌ في الخادم يُسقط الاثنين.** لا عزل.
3. **الموارد تُقتسم.** بناءُ صورة هاي روت يستهلك ذاكرة بجانب موازين العامل.

---

## 1. قبل أن تبدأ — ثلاثة جاهزة

| ما يلزم | كيف تتحقّق |
| --- | --- |
| **DNS** لنطاق هاي روت يشير إلى `54.162.172.204` | `nslookup نطاقك` يعيد العنوان |
| منفذا 80 و443 مفتوحان في Security Group | مفتوحان أصلًا لموازين |
| ملف `.pem` للدخول | تعرف مساره على جهازك |

**انتظر انتشار DNS قبل الخطوة ٥**: Caddy تطلب شهادة Let's Encrypt عند أول
طلب، وطلبٌ على نطاقٍ لا يشير إلى الخادم **يُخفق ويُحسب في حدّ المحاولات**.

## 2. الدخول وجلب المشروع

```bash
ssh -i مفتاحك.pem ubuntu@54.162.172.204
```

```bash
cd /srv && git clone https://github.com/hishare24-sketch/hiroote.git && cd hiroote
```

> شغّل `git` و`docker` **كـ ubuntu بلا `sudo`** — الوصول إلى GitHub يعمل
> كـ ubuntu وحده على هذا الخادم.

---

## 3. البيئة

```bash
cp .env.production.example .env
```

ولّد المفتاحين الوحيدين اللذين لا يُخترعان:

```bash
docker run --rm php:8.4-cli php -r 'echo "base64:".base64_encode(random_bytes(32)),"\n";'
```

```bash
openssl rand -base64 32
```

الأول `APP_KEY`، والثاني `DB_PASSWORD`. ثم `nano .env` واملأ:

| المتغيّر | القيمة |
| --- | --- |
| `APP_KEY` | الناتج الأول كاملًا مع `base64:` |
| `APP_URL` | `https://` ثم نطاقك |
| `DB_PASSWORD` | الناتج الثاني |
| `GATEWAY_NETWORK` | تأكّده بـ `docker network ls \| grep app` |

> ⚠️ **`APP_KEY` يُولَّد مرة واحدة إلى الأبد.** أسرار جسور المشاريع وتوقيعات
> التنبيهات مشفَّرة به، فتغييرُه يجعلها كلها غير قابلة للفكّ — بلا رسالة خطأ
> واحدة، إلى أن يُخفق أول نداء ولا يُعرف السبب. احتفظ به خارج الخادم.

---

## 4. أول نشر

```bash
bash scripts/deploy.sh
```

يسحب `main`، ويبني الصورة، ويُقلع القاعدة و Redis، ثم **يهاجر** ثم يُقلع
التطبيق والطابور والمجدول. وأي خطوة تُخفق توقف ما بعدها.

ثم أنشئ أول مدير — القاعدة المهاجَرة فيها مشروع ولا مستخدم فيها:

```bash
docker compose -p hiroote -f docker-compose.prod.yml exec app php artisan hiroote:bootstrap
```

يسأل عن الاسم والبريد وكلمة المرور (١٢ محرفًا فأكثر)، ويمنح الحساب عضوية
**مدير النظام في كل مشروع**. ويرفض العمل إن كانت القاعدة تحوي حسابات — فهو
لأول إقلاع وحده.

> **لا تشغّل `db:seed` على الإنتاج.** البذرة تنشئ ستة حسابات بكلمة المرور
> `password` وتزرع حركةً تجريبية تُقرأ في اللوحة حركةً حقيقية.

## 5. ربط البوّابة

في **مستودع موازين** على الخادم:

```bash
cd /srv/mazeen/app
```

١) أضف كتلة الموقع من `deploy/Caddyfile.hiroote` (في مستودع هاي روت) إلى نهاية
`Caddyfile`.

٢) أضف المتغيّر إلى خدمة caddy في `docker-compose.prod.yml`:

```yaml
    environment:
      DOMAIN: ${DOMAIN:?ضع DOMAIN=your-domain.com في ملفّ .env}
      HIROOTE_DOMAIN: ${HIROOTE_DOMAIN:?ضع HIROOTE_DOMAIN في .env}
```

٣) أضف `HIROOTE_DOMAIN=نطاقك` إلى `.env` هناك.

٤) **تحقّق من الصيغة قبل أي شيء** — هذه الخطوة تفصل بين تعديلٍ ينجح وموقعٍ
يسقط:

```bash
docker exec mazeen-staging-caddy-1 caddy validate --config /etc/caddy/Caddyfile
```

٥) إن قالت `Valid configuration`، أعد التحميل بلا انقطاع:

```bash
docker compose -f docker-compose.yml -f docker-compose.prod.yml up -d caddy
```

`up -d` لازمة لا `reload`، لأن المتغيّر الجديد يصل الحاوية عند إعادة إنشائها
فقط. وموازين ينقطع ثوانيَ معدودة.

---

## 6. التحقّق — النشر لا يُعدّ ناجحًا قبله

| الفحص | المتوقَّع |
| --- | --- |
| `docker compose -p hiroote -f docker-compose.prod.yml ps` | خمس حاويات `Up` |
| فتح النطاق | صفحة الدخول بشهادة صالحة |
| الدخول بالحساب الذي أنشأته | لوحة النظرة العامة |
| `… logs --tail=20 scheduler` | أسطر جدولة لا أخطاء |
| `… logs --tail=20 queue` | العامل يعمل بلا تكرار سقوط |
| فتح `mawazinswift.com` | **يعمل كما كان** |

الأخير ليس تزيّدًا: تعديل بوّابته وقع للتوّ.

---

## 7. النشر اللاحق

```bash
cd /srv/hiroote && bash scripts/deploy.sh
```

الصورة تُبنى من جديد، والحاويات تُستبدل. الانقطاع ثوانٍ.

## 8. النسخ الاحتياطي — ابدأه من اليوم الأول

قاعدة هاي روت تحمل ما لا يُشترى مرتين: سجلّ التدقيق، وقاعدة المعرفة، وأسرار
جسور المشاريع.

```bash
docker compose -p hiroote -f docker-compose.prod.yml exec -T pgsql \
  pg_dump -U hiroote hiroote | gzip > ~/hiroote-$(date +%F).sql.gz
```

ونسخةٌ على الخادم نفسه ليست نسخة احتياطية: انقلها خارجه. **و`APP_KEY` يُحفظ
معها** — نسخةٌ بلا مفتاحها تُستعاد ناقصةً كل سرٍّ فيها.

---

## 9. ما بعد النشر — إشعال التكامل مع موازين

بعد أن يصير هاي روت على عنوانٍ حقيقي:

1. **المشاريع ← موازين ← المفاتيح ← إصدار** — مفتاح إنتاج، يُعرض مرة واحدة.
2. في موازين: `HIROOTE_BASE_URL` و`HIROOTE_API_KEY` في `backend/.env`
   **و`docker-compose.yml` معًا** (`docs/09 §3.1`).
3. أبطِل المفتاح المحلّي القديم.
4. تحقّق بالمتصفّح — البند الوحيد الذي لم يُغلق في `docs/09 §7`.
